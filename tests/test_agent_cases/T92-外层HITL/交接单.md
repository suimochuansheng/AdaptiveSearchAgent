## 1. Spike 三问（`scripts/spike_tool_interrupt.py`）

运行：`poetry run python scripts/spike_tool_interrupt.py`（langgraph 1.2.11 / langchain-core 1.6.3）

### Q1：工具函数里 `interrupt(payload)`，ToolNode 执行时流里能否观察到 `__interrupt__`？

**答：能。**

- 中断不是独立 stream mode；它出现在 **`stream_mode="values"` 的 payload 字典**里：
  `mode='values'`，`payload` 的键为 `['messages', '__interrupt__']`，
  值是 `(Interrupt(value={八字段}, id='…'),)`。
- 生产帧循环用的 `stream_mode=["messages","values"]` 下观察到的 mode 序列：
  `['values', 'messages', 'values', 'values']`，中断命中的是最后一个 `values`。
- 机制成立的原因：`ToolNode._execute_tool_async` 对 `GraphBubbleUp` 显式 `raise`
  （`langgraph/prebuilt/tool_node.py` 注释写明"GraphInterrupt raised inside a tool"），
  所以工具内的中断能冒泡成节点中断。

### Q2：`Command(resume=值)` 重推同一 `thread_id`，能否续跑且 `interrupt()` 返回该值？

**答：能。**

```text
中断后执行次数：0（应为 0）
中断后 next 节点： ('tools',)
恢复后执行次数：1（应为 1）
interrupt 收到的值：'approve'
最后一条消息：ToolMessage content='danger_tool 已执行，decision=approve'
```

要点：恢复时 LangGraph 会**从头重跑**被中断的工具函数，`interrupt()` 这次直接返回 resume
值而不是再抛；执行计数 0 -> 1，说明"挂起时不执行、恢复后恰好执行一次"。

### Q3：中断期间，现有 `src/conversation_stream.py` 帧循环会不会卡死 / 抛异常？

**答（改造前）：不卡死、不抛异常，但会把中断静默吞掉。**

- 首跑（未改帧循环）输出：帧类型 `['tool_call', 'final']`，`final` 的 `content` 为空串，
  用时 0.00s，`error=None`。原因：`__interrupt__` 是 `values` payload 的一个键，
  原 `_consume` 把它当普通 values 快照，只更新 `snapshot["final"]`，不识别中断。
- **已修**：`stream_conversation` 在 values chunk 里识别 `__interrupt__`，调用
  `agent/adapters/api/hitl.py::build_interrupt_frame` 产出 `interrupt` 帧后 `break`，
  且本轮**不发 final**（等 `/resume` 续跑）。修后复跑 spike：
  `帧类型 ['tool_call', 'interrupt']`、`是否出现 interrupt 帧：True`、未卡死。
- 开关关闭 / 无中断时该分支不触发，帧序列与改造前逐帧一致（不变量回归见 §6）。

**结论：Q1/Q2 均为"是"，不触发停手条件；Q3 的问题已在本卡顺手修掉。**

## 4. 状态码矩阵（`POST /chat/conversation/{thread_id}/resume`）

请求体：`{"approval_id": str, "decision": "approve"|"reject", "request_id": str}`。

| 顺序 | 条件 | 码 | 实现位置 |
|---|---|---|---|
| 0 | `ENABLE_HITL=False`（审批未启用） | **404** | `resume_conversation` 首行 |
| 1 | `request_id` 24h 内重复 | **409** | `approval_store.remember_request`（`SET NX`） |
| 2 | `approval:<id>` 不存在且墓碑 `consumed` | **409**（已消费/重放） | `_raise_by_tombstone` |
| 3 | `approval:<id>` 不存在且墓碑 `issued` | **410**（过期） | 同上 |
| 4 | `approval:<id>` 从未存在（无墓碑） | **404**（未知凭据） | 同上 |
| 5 | 凭据存在但 `thread_id` 不匹配 | **409** | `stored.thread_id != thread_id` |
| 6 | 会话无 pending interrupt | **409** | `graph.aget_state(...).next` 为空 |
| 7 | 同一会话已有 resume 持有 `agent_lock:<thread>` | **409** | 复用 Redis 会话锁，非阻塞获取 |
| 8 | 原子消费失败（并发输家 / 已消费） | **409** / **410** | Lua 返回 nil 后查墓碑 |
| 9 | Redis 不可用 / 状态读取异常 | **404**（fail-closed，不执行） | 契约只有四码，未引入 503 |
| 10 | 校验通过 | **200 + text/event-stream** | `Command(resume=decision)` 续跑 |

> 说明：契约 §4 把"已消费"定为 409、"过期"定为 410，而 Redis 里两者都表现为
> `approval:<id>` 不存在。因此墓碑写成两个值：创建时 `issued`，消费成功后 `consumed`；
> 查询按值分流。这样验收第 5 条（重发 409）与第 7 条（过期 410）同时成立。

## 7. 已知未做 / 限制

1. **依赖链条**：审批只在 `ENABLE_TOOL_POLICY=True` 时生效（`wrap_tool` 默认不包装）。
   只开 `ENABLE_HITL` 不开工具策略 -> 零包装、零审批（G5 原设计）。验收/联调需两个都开。
2. **`task_states` 未改**：现有 `/chat/conversation` 在流结束后仍写 `completed`；本卡只允许
   `api_main.py` 加一行注册，因此没改它的状态机。resume 判定依据是 **checkpoint 的 pending
   interrupt**（`graph.aget_state().next`），不依赖 `task_states`，功能不受影响；但用
   `/chat/stream` 那套状态机观察此会话时会看到 `completed` 而不是 `interrupted`。
3. **同轮多工具的"恰好一次"**：ToolNode 把同一轮的多个 tool_call 放在一个节点任务里；
   中断恢复会重跑整个 tools 节点，因此**同批次其他工具可能执行两次**。验收场景（单个危险
   工具）恰好一次。批次级幂等未做。
4. **同轮多个并发审批**：resume 只传单值 `Command(resume=decision)`；若同一轮多个危险工具
   同时中断，需要 resume 列表/字典，本卡未实现（当前模型单工具调用为常态）。
5. **Redis 不可用的状态码**：契约只冻结 200/409/410/404；为了不引入第五码且 fail-closed，
   resume 返回 **404**（"审批服务不可用，已拒绝"）。执行器侧签发失败时返回可读拒绝文案，
   不调用工具。
6. **`tool_call_id` 获取方式**：通过 LangGraph 内部 `config["configurable"]["__pregel_read"]`
   读当前 `messages`，按"工具名 + 参数"匹配。取不到时为空串（类型仍满足契约），不影响
   续跑（resume 由 interrupt 序号驱动）。这是内部接口，已用异常兜底。
7. **子图 cost_confirm**：当前 `_build_research_graph()` 用 `include_hitl=False` 编译，子图
   中断不会出现；代码仍按 `approval_id` 过滤——将来子图中断不会被误当成外层审批弹卡，
   但外层流也会跳过它（"留在子图"）。
8. **OI-INT-002 的实现细节**：LangChain 1.6 的同步回调走 `run_in_executor` +
   `copy_context()`，contextvar 到不了回调线程；且 `on_tool_end` 收的是 `ToolMessage`。
   因此结果码读取是三路兜底：contextvar -> `tool_call_id` 索引 -> 返回值/异常对象属性。
   contextvar 仍是第一读取源；契约未变。
9. 前端断言（G9）与 TDM 假 SSE 服务未在本卡重跑；本卡只保证帧格式与契约一致。
10. 未写台账（按指令）。
