## 5. 判定口径（两处需要说明，避免复验歧义）

1. **"文档里不出现 token"按字段级判定**：`approval.md` 必须写明 `approval_id` 由
   `secrets.token_hex(16)` 生成（卡面要求），该标识符本身含 `token` 子串，所以字面 grep 不可能为 0。
   `t12_checks.py` 用 `(?<!\w)token(?!\w)` 判"独立词"：契约正文 0 处，历史段 1 处（删除记录），
   dataclass 字段 0 处、resume body 键 0 处。证据见 T12-012。
2. **迁移卡是消费方，不是改契约的地方**：md 里的 `<!-- t12:... -->` 注释块是机读锚点，
   改字段必须同时改 md 表、dataclass、`t12_checks.py` 顶部常量与 `event_version`（新开修订文件）。
3. **TDM-B2 的基线会随"最后改过 `frontend/app.py` 的提交"移动**：B2 用
   `git log -1 -- frontend/app.py` 取上一个版本做 AST 对比，0a 提交后基线变成"含 token 的 G9 版"，
   `_build_resume_body` 必然显示为"被改写"。因此把该函数加进 `_ALLOWED_CHANGED_DEFS`
   （连同注释与 docstring 口径），旧 `/chat/stream` 流程的其余定义仍逐 AST 冻结。
   **这不是放宽验收**：函数改动本身就是卡面 0a 要求的；B2 仍会抓任何其他旧定义变动。
   （提交前 21/21 是因为当时基线还是更早的提交，碰巧不含该函数。）
