## 1. 设计决策（按需求 4 条执行）

1. **不起服务、不加前端、不新增依赖**：界面只有 `python -m evals.*` + `report.md`；
   评测执行器按配置起**已存在的** `api_main:app` 子进程（跑完即停），不是新增服务组件。
2. **门禁逻辑与真实评测解耦**：`evals/run.py` 真跑模型；`evals/gate.py` 的 `compare()` 是纯函数
   （零 IO、零模型调用）；CI 只跑 `scripts/smoke_eval_gate.py` 的 fixture 自测。
   边界写在 `docs/eval-gate.md` 开头。
3. **判据沿用既有口径**：`abs(candidate_mean - baseline_mean) <= recorded_variance`
   （默认 `0.0408`，来自 `docs/baseline.md` §4 的 Ragas 两次实测差）；单题差值只归因，
   不改判 PASS/FAIL。
4. **新结果只写 `evals/results/`**：`docs/baseline.md` 的 §7/§8 数字未改；
   `config.py` 的开关默认值未改；`evals/results/` 已加入 `.gitignore`。

## 4. 已知边界

- **判据是双侧的**：`abs(delta) <= 0.0408`。提升幅度超过方差同样判 FAIL（表示变化超出记录噪声）；
  smoke 的“提升”fixture 因此用 `+0.03`（在方差内）验证 PASS。若业务只想惩罚退化，
  需要窗口明确把判据改成单侧——本卡按需求给的 `abs` 原文实现，没有擅自改。
- **0.0408 来自 Ragas 的 0~1 指标**（faithfulness 两次差），迁到 1~10 分 judge 上非常紧：
  单题 ±1 分即可让 20 题均值动 0.05。门禁只做“稳定性”判定，不替代人工归因。
- **单裁判、20 题样本小**：换 `EVAL_JUDGE_MODEL` 后不可横比；meta 记录 judge_model，
  但 `compare()` 不强制校验，跨裁判比较会得到无意义结论。
- **CI 不跑真实评测**：没有模型凭据，只验证门禁逻辑；真实质量仍需本地/发版前跑 `evals/run.py`。
- **`tokens` 可能为 null**：`/chat/conversation` 的 SSE 没有 kpi 帧；字段保留，报告不据此判定。
- **比较至少需要 2 道共同有效题**：`--limit 1` 的 run 可落库、可出报告，但不能用于门禁判定（退出码 2）。
  本次验收的 run 2/1 题混跑就触发了这条边界。
- **真实评测依赖环境**：后端需要 Postgres/Redis（本项目 `redis_cache` 在 16379）；
  RAG 网关 8100 不通时分数会很低（本次即如此），但不影响“落库/对比/报告”链路。
- **配置 C 的 `EVAL_AUTO_APPROVE=1` 仅评测用**：与 `docs/baseline.md` §8 C 组同口径；
  `ENV=prod` 时被忽略。
- 失败归因是启发式（工具未调用 / 答案退化 / 超时 / 报错），只影响失败清单，不参与 PASS/FAIL。
- 未 push；未写台账行（TEG 行由测试窗口写）；未改 `docs/baseline.md`、`config.py` 默认值、`ci.yml`。
