## 10. 拒绝后消息未渲染修复（2026-11-24 / S3）

### 10.1 现象（用户实测）

会话模式下：发一句触发审批的问题 → 点「拒绝」→ 看到「已拒绝执行」→ **立刻**在输入框发
「那你先说说你知道的」→ 后端确实在跑（有回答、日志有请求），但**这句用户消息没有出现在
对话流里**；截图效果是「agent 无缘无故开始回答」。

### 10.2 取证（未先改代码）

用 python-socketio 直接扮 Chainlit 前端连真实 `:8202` + 真实 `:8201` 后端，复现同一调用序列，
逐帧记录服务端事件；后端请求行另从 uvicorn 日志统计。关键事实：

| 观测 | 数值 |
|---|---|
| 拒绝 → 本轮 `task_end`（旧实现） | **48.4s** 才到（resume 流没吐完就不结束） |
| 拒绝 → resume 首 token | **25.3s** |
| 拒绝后的 resume 续写长度 | **3095 字**（一整篇"深度调研报告"） |
| 旧实现下拒绝后 1s 发新消息 | 后端 `429 Too Many Requests`「该会话正在执行中」 |

结论（对"根本没生成 / 生成了但没 send"的回答）：**Chainlit 消息列表里从来没有这条消息**。
用户消息在 Chainlit 2.12 里是前端乐观渲染（`MessageComposer.onSubmit → sendMessage`：
先 upsert 进消息列表，再 `socket.emit("client_message")`），服务端从不回显 user_message。
所以"对话流里没有"只能是**客户端的 `submit()` 直接 return**：`MessageComposer.submit()` 第一句
`if (disabled || ...) return;`，而 `disabled = !connected || loading || ask.spec.type in
(file, action, element)`（react-client `useChatData`）；`loading` 在本轮 `task_end` 前一直为真。
拒绝后 resume 续写把本轮拖住 48s，这 48s 里输入框能打字但**按发送无效**，
既不入列表也不 emit —— 屏幕上出现的"回答"其实是拒绝分支的续写报告。

### 10.3 四个假设的排除结论

- **H1 提前 return**：不成立。`on_message` 里没有"仍在审批态就跳过"的分支；`_resume_conversation`
  的 `return` 只回到 `_on_conversation_message`，`break` 只跳出审批 while 循环，都不影响下一条消息
  进入 `on_message`（下一条消息照常走到 `_stream_conversation`）。
- **H2 重复/缺失 send**：不成立。全文件没有 `cl.Message(author="User")` 之类的手工补发；
  用户气泡完全由 Chainlit 客户端渲染，前端不该也不能替它发。
- **H3 状态标记未复位**：不成立。`cl.user_session` 只有 `thread_id / user_name / chat_mode /
  upload_history`，没有任何"等待审批"flag；拒绝后 `_PENDING_*` 之外的会话状态一律没写。
- **H4 异常被静默 catch**：不成立。三处 `except` 都 `logger.exception` 并写可读错误气泡；
  复现全程无异常、无 `❌ 执行出错` 气泡，请求也确实到达后端（旧实现是 429，不是被吞）。

真正的拦路点不在异常、也不在 send，而在**本轮迟迟不结束**（见 10.4）。

### 10.4 根因（一句话）

拒绝分支同步 `await` 了 resume 的整条 SSE（后端拒绝后还会继续跑 25~48s、续写 3095 字），
本轮一直 running → Chainlit 2.12 在 running 期间禁用输入框提交，用户"立刻"发的下一句被
`submit()` 静默丢弃（不入列表、不 emit），而后端的续写报告被渲染成"无缘无故的回答"。
