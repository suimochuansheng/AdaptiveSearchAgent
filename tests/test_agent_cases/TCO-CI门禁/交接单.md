## 4. `scripts/ci_check_ledger.py` 设计

- 默认读 `tests/test_agent_cases/台账用例.csv`，`--file` 可指向任意台账（便于自测/负向验证）；
- 只读、零第三方依赖（`argparse` / `csv` / `io` / `re` / `sys` / `pathlib` / `collections`）；
- 校验项与输出：

  | 项 | 规则 |
  |---|---|
  | 解码 | 能按 GB18030 解码；若内容同时是 UTF-8（含非 ASCII 字节）判 BAD |
  | 表头 | 15 列，且列名与约定表头逐列一致 |
  | 行宽 | 每条数据行 15 列 |
  | case_id | 非空、唯一、匹配卡号正则 |
  | status | ∈ {pass, fail, block} |
  | open_issue | `status != pass` 的行必须非空 |
  | last_run | `YYYY/MM/DD` 或空 |

- 每项一行 `[OK]/[BAD] 项 — 证据`，行级问题追加 `[BAD] 第 N 行 ...`；
  末行 `LEDGER: n rows, m problems`；`m > 0` 退出 1。

**两处与需求文字的偏差（均已在代码注释中说明）：**

1. **case_id 正则**：需求写 `^[A-Z]+-\d{3}$`，但台账实际有 182 行形如 `T01-001` 的卡号
   （前缀带数字），按字面正则会全部误杀、验收不可能为 0 problems。实现放宽为
   `^[A-Z][A-Z0-9]*-\d{3}$`（字母开头、前缀可含数字、连字符后固定 3 位数字），
   仍能拦住小写、空格、位数不对、缺连字符等脏值。
2. **"status 改 pass 但留空 open_issue"不是违规**：规则是"非 pass 行 open_issue 必填"，
   `pass` 行留空完全合法（本台账 265 行 pass 中大量 open_issue 为空）。因此负向验证改用
   "block 行清空 open_issue"与"删一列"，见 §6。

## 6. 负向验证（证明门禁真会拦）

### 6.1 台账体检 —— 两类反例都退出 1 并给出行号

反例 A：把第 24 行（`T02-005`，block）的 `open_issue` 清空（`/tmp/bad_open_issue.csv`）：

```text
[BAD] open_issue — 1/4 行非 pass 却留空
[BAD] 第 24 行 (T02-005) open_issue — status=block 但 open_issue 为空
LEDGER: 269 rows, 2 problems
EXIT=1
```

反例 B：删掉最后一列（`/tmp/bad_width.csv`，全部数据行变 14 列）：

```text
[BAD] 行宽 — 269/269 行不是 15 列
[BAD] 第 2 行 行宽 — 14 列，期望 15 列
…（逐行报到第 270 行）
LEDGER: 269 rows, 270 problems
EXIT=1
```

对照：按需求原话把某 block 行改成 `status=pass` 且 `open_issue` 留空，体检输出
`LEDGER: 269 rows, 0 problems`、EXIT=0 —— 这是**规则本身允许**的形态，不是漏检（见 §4 偏差 2）。

### 6.2 lint-imports —— 契约删除 ≠ 红，真实越界才红

按要求"临时注释掉 `app-independent` 契约"后执行 `poetry run lint-imports`：

```text
core-no-framework KEPT
adapters-only-ports KEPT
Contracts: 2 kept, 0 broken.
LINT_EXIT=0
```

**结论：删契约不会让 lint-imports 变红**（少一条契约只是少检查，没人报 broken）。这正是
T11-001（contract 名 3/3）与 T11-008（pyproject 必须 3 条）存在的价值，两步骤在本 CI 里
前后相邻，删契约会在 T11 步骤被拦下。需求里"注释契约 → lint-imports 报错"的预期与实际
工具行为不符，特此记录。

真实越界探针：向 `agent/domain/__init__.py` 追加 `import langchain_core`，执行
`poetry run lint-imports`：

```text
Broken contracts
core-no-framework
agent.domain is not allowed to import langchain_core:
-   agent.domain -> langchain_core (l.7)
LINT_EXIT=1
```

探针与注释契约均已还原（`cp` 备份 + `git status` 复核为干净），未留改动。

## 7. 阻塞项（本卡唯一未达标项）：T63-012 在 HEAD 上必然红

实测 `t63_checks.py` 为 `19 passed, 1 failed`，失败项：

```text
[FAIL] T63-012 B1 src/tools 零改动且 graph 仅 contextvar —
AssertionError: 工作区 src/tools 仍有改动：['src/tools/offload.py']
```

根因（与本次改动无关）：

- `t63_checks.py` 把 `DEV_COMMIT = "423c1ea"`（T6-3 开发提交，2026-11-11）写死，并用
  `git diff --name-only 423c1ea -- src/tools` 判断"工作区"是否改动；
- 该命令比较的是 **423c1ea 与当前工作树（含其后所有提交）**，不是 `git diff`（HEAD vs 工作区）；
- 其后 `c0fefec`（T6-5 工具输出注入防护，2026-11-12）合法地改了
  `src/tools/offload.py`（引入 `untrusted.wrap` 等），于是这条断言在 HEAD 上永远失败。

```text
$ git diff --stat 423c1ea -- src/tools
 src/tools/offload.py | 11 ++++++++++-
 1 file changed, 10 insertions(+), 1 deletion(-)
```

建议（**未执行**，属测试窗口改动，本卡不变量禁止改测试断言）：把该行改为
`git diff --name-only -- src/tools`（只看未提交改动），或把基线推进到 T6-5 之后的提交。
在修复前，CI 的 T63 步骤会稳定失败——这正是门禁应有的行为，不是本卡配置错误。
