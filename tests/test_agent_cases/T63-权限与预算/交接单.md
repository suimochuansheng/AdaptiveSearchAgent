## 4. 设计要点与关键取舍

1. **策略是纯函数**：`decide()` 不读 `config`、不读时钟、不 IO。两个上限通过
   `PolicyContext.max_calls / cost_limit` 注入（默认 8 / 2.0，与 `config.py` 一致），
   测试可以直接构造边界值。
2. **规则顺序即契约**（短路）：审批 → 调用次数 → 费用 → 允许。
   `requires_approval is True` 排第一，所以 `deep_research` 在“预算内/超限”三种场景下
   都给 `approval_required`（冒烟表可见）。
3. **timeout 不进 `decide`**：超时是执行期事实，由 executor 的
   `asyncio.wait_for` 兜住并返回可读错误；放进策略会被误判为“策略拒绝”，也无法记账。
4. **计价 v1 = 一次调用 1 个 unit**：`cost = cost_model.unit_cost`。`unit="keyword"` /
   `"token"` 的细分留到有真实计价需求时再做（策略要保持纯函数，不解析工具参数）。
   对 `search_tavily` 这种按词计价属于**已知少记**，不是 bug。
5. **作用域走 contextvar**：`tools_node` 用 `with tool_scope(thread_id)` 设置；拿不到时
   兜底 `"unknown"` 并只 `warning` 一次（不崩）。
6. **账本端口同步/异步双兼容**：`BudgetLedger` 方法注解为 `T | Awaitable[T]`，内存实现
   同步、Redis 实现异步，执行器用 `inspect.isawaitable` 统一收口；调用方两种都能直接用。
7. **Redis 降级**：未配置 `REDIS_URL` / 连不上 / 命令报错 → 只 `warning` 一次，之后
   快照恒 0（Noop 语义），工具照常执行，会话不中断。
8. **默认关闭零影响**：`wrap_tool()` 在 `ENABLE_TOOL_POLICY=False` 时**原样返回 `fn`**
   （`is` 同一对象），`tool_scope()` 只 `yield` 不碰 contextvar、不产生 token。
   `to_lc_tools()` → `TOOLS` → `bind_tools`/`ToolNode` 的路径与改造前逐字节一致。
9. **schema 不变靠 `functools.wraps`**：包装后 `inspect.signature` 跟随 `__wrapped__`，
   `__name__` / `__doc__` 同步复制；`wrap_tool` 在返回前断言签名一致，冒烟脚本再回验
   schema sha256（开/关都是基线值）。
10. **超时收尾**：目标任务 `cancel()` + `gather(..., return_exceptions=True)`，
    实测无 “Task was destroyed but it is pending” 泄漏（见第 3 条证据）。

## 5. 开关矩阵

| `ENABLE_TOOL_POLICY` | `to_lc_tools()` | `tool_scope()` | 运行时行为 |
|---|---|---|---|
| **False（默认）** | 返回原函数（identity） | 空转，不设 contextvar | 与改造前逐字节一致：不判定、不超时、不记账、不连 Redis |
| **True** | 返回 `wrap_tool` 包装 | 设置 `thread_id` | 每次调用先 `decide()`，再执行 / 超时 / 异常归一，最后记账 |

附加参数（仅开关开启时生效）：

| 字段 | 默认 | 含义 |
|---|---|---|
| `TOOL_MAX_CALLS_PER_TURN` | 8 | `used.calls >= 8` → `denied_calls`（第 9 次被拒） |
| `TOOL_SESSION_COST_LIMIT` | 2.0 元 | `used.cost + 本次成本 > 2.0` → `denied_cost`（恰好等于 2.0 仍允许） |

## 8. 已知未做 / 已知偏差（都写清楚了，不是遗漏）

1. **HITL 审批未实现**：`require_approval` 只返回固定文案
   `该工具需要人工审批后才能执行（HITL 未启用，本次已拒绝）`；
   换成 `interrupt` 与审批卡片是 G7/T9-2 的活。
2. **`ApprovalThreshold` 未实现**：`decide()` 只认 `requires_approval is True`
   （bool 形态）；对象形态（阈值）按“不强制审批”继续往下走，留给 G7。
3. **计价 v1 是近似**：一次调用 = 1 个 unit，`keyword` / `token` 细分为未做，
   `search_tavily` 会少记费用（2 分/词只按 2 分/次记）。
4. **`scope = thread_id`，不是“每轮”**：`TOOL_MAX_CALLS_PER_TURN` 实际是
   “同一 thread 在账本 TTL 内累计 8 次”。要严格“每轮重置”，需要 executor 在每轮
   开始时 `ledger.reset(scope)` 或把 calls 的 scope 拆成 `thread:turn`——
   本卡按卡面“scope 用 thread_id”落地，未擅自加轮次状态；差异在此显式记录。
5. **Redis 并发 ±1 次误差**：`snapshot → decide → add` 非原子；v1 接受多放 1 次，
   未做 Lua 原子化（见 `budget_redis.py` docstring）。
6. **未改 `src/tools/*`**：超预算收口继续复用现成的
   `src/tools/offload.py::shrink_tool_message`，本卡没有重复实现 shrink/offload。
7. **`estimate_tokens` 复用现成实现**：executor 从 `src/context_manager.py` 导入，
   没有复制一份口径（代价是 adapters 依赖一个 src 工具函数；迁移期可接受）。
8. **日志用标准库 `logging`**：`agent/` 目前没有统一 logger，本卡用
   `logging.getLogger(__name__)`，便于 caplog 捕获；后续 `agent/` 有了自己的
   logger 适配器再统一。
9. **未写台账**：按卡面要求，本卡起恢复“测试窗口写台账”，开发窗口不碰
